### 4. BAse64 encoding

Base64 encoding is a way to represent binary data (like images, files, or bytes) in a text format using only printable ASCII characters.

**Why Use Base64?**
Many systems (like JSON, HTML, or URLs) expect text, not binary data. Base64 solves this by turning binary into text — safely and compactly.

**Important Notes**
* Base64 increases size by ~33%
* It is not encryption – anyone can decode it
* Used for transport, not for security

### 5. Diff types of Encoding

1. Character Encoding

| Encoding       | Description                                   | Example         |
| -------------- | --------------------------------------------- | --------------- |
| **ASCII**      | Basic 7-bit character encoding (English only) | A = 65          |
| **UTF-8**      | Most popular, supports all Unicode characters | 😊 = 4 bytes    |
| **UTF-16**     | Unicode, fixed 2 or 4 bytes                   | Used in Windows |
| **UTF-32**     | Unicode, fixed 4 bytes per character          | Rarely used     |
| **ISO-8859-1** | Latin-1, Western European languages           | Legacy systems  |

   
2. Binary-to-Text Encoding
   
| Encoding         | Purpose                                   | Notes                      |
| ---------------- | ----------------------------------------- | -------------------------- |
| **Base64**       | Encode binary to ASCII text               | Common for files, JWT      |
| **Base32**       | Like Base64 but case-insensitive          | Useful in QR codes         |
| **Base58**       | No confusing characters (like 0, O, l, I) | Used in Bitcoin addresses  |
| **Hex (Base16)** | Each byte is two hex digits               | Easy to debug (e.g., 0xAF) |

3. Encryption (Not Really Encoding)

| Encoding        | Encryption          |
| --------------- | ------------------- |
| Reversible      | Reversible with key |
| Not secure      | Secure              |
| Used for format | Used for secrecy    |

**When to Use What?**
| Use Case                        | Recommended Encoding      |
| ------------------------------- | ------------------------- |
| Web URLs                        | URL Encoding              |
| Storing emoji/multilingual text | UTF-8                     |
| Embedding image in HTML         | Base64                    |
| Serializing binary in JSON      | Base64 or Hex             |
| Secure data transmission        | Encryption (not encoding) |

### JWT, Access Tokens, and Refresh Tokens

<details>
   <summary> DETAILS </summary>

A JSON Web Token (JWT) is a compact format for carrying claims. The common **signed JWT** has three Base64URL-encoded parts separated by dots:

```text
header.payload.signature
```

- **Header:** Token metadata, usually the type (`JWT`) and signing algorithm (for example, `RS256`).
- **Payload:** Claims such as `sub` (subject), `iss` (issuer), `aud` (intended API), `exp` (expiration time), and `iat` (issued-at time).
- **Signature:** A cryptographic value calculated over the encoded header and payload. The API verifies it to detect tampering and confirm the token was signed with a trusted key.

The header and payload of a signed JWT are encoded, not encrypted, so they can usually be read by anyone who has the token. Do not put secrets in them.

An **encrypted JWT** has a different, five-part structure:

```text
header.encrypted_key.initialization_vector.ciphertext.authentication_tag
```

So `header.payload.signature` describes the usual signed form, not every possible JWT.

### Access and refresh tokens

“Access” and “refresh” describe what a token is used for; “JWT” describes a token format.

- **Access token:** Sent to an API to access protected resources. It may be a JWT or an opaque string and is typically short-lived.
- **Refresh token:** Sent to the authorization server to request a new access token. It is usually long-lived, handled carefully, and commonly opaque.

Access and refresh tokens are different token roles, not two parts of one JWT.
Either role can have an implementation-specific format, though JWTs are commonly used for access tokens and opaque values for refresh tokens.

```text
Client ── access token ──> API
Client ── refresh token ─> Authorization server ── new access token ─> Client
```

### how does the JWT token is validated - when user / application tries to authenticate using this JWT how its validated from session issuer / store

<details>
   <summary> DETAILS </summary>
</details>

A JWT usually isn't looked up in a session store when it's used. The API validates the token itself using rules and keys it trusts from the issuer. A database or cache check is an optional extra for revocation or current account status.

### Validation flow

1. **The client sends the token** with its request, usually as `Authorization: Bearer <token>`.
2. **The API reads the token's header and claims.** A signed JWT is encoded, not necessarily encrypted, so its contents can usually be read. The API must not trust the claims until validation succeeds.
3. **The API verifies the signature.** The issuer signed the token with a private key; the API checks it with the corresponding public key. With a shared-key setup, issuer and API use the same secret.
4. **The API checks the expected values**, such as:
   - `iss`: Was it issued by a trusted issuer?
   - `aud`: Was it meant for this API?
   - `exp` and, if present, `nbf`: Is it currently within its validity period?
   - The expected signing algorithm and token type.

If a check fails, the API rejects the request, usually with `401 Unauthorized`. Microsoft’s [ASP.NET Core JWT bearer guidance](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0) lists signature, issuer, audience, and expiry among the validations APIs should perform.

### Where the issuer's keys come from

For a public/private key setup, the API is configured to trust an issuer, often through an `Authority` URL. It can use the issuer's metadata to find its public signing keys, commonly published as a JWKS document. The API caches these keys and uses them to validate tokens locally; it generally doesn't call the issuer for every API request. The [JWT Best Current Practices (IETF RFC 8725)](https://datatracker.ietf.org/doc/html/rfc8725.html) says the application must ensure that the signing key belongs to the claimed issuer.

```text
Login: client ──credentials──> identity provider
       client <──signed JWT─── identity provider

API call: client ──JWT──> API
                         ├─ verify signature with trusted key
                         ├─ check issuer, audience, and time claims
                         └─ optionally check database/cache for revocation
```

### When a store is involved

With ordinary self-contained JWT validation, the API doesn't ask a session store, “Does this token exist?” That's why a token can remain usable until it expires—even if the user changes their password—unless the system adds a revocation check.

A system can add a database or cache lookup on each request, for example, to compare the token's `token_version` with the user's current value, check that an account is active, or confirm that a particular session ID still exists. That can revoke tokens sooner, but adds a dependency and request cost.

This differs from **opaque tokens**, which don't carry locally verifiable claims; an API may need to ask an authorization server whether one is active. For JWT access tokens, the usual pattern is local signature and claim validation, with an optional store check when the application needs early revocation.

### Authentication and authorization

Successful token validation means the request has an acceptable identity token. The API still needs **authorization** checks to decide whether that identity may perform the requested action.

### How to Revoke a JWT Before It Expires. 

<details>
   <summary> DETAILS </summary>
Other REF:- https://milanjovanovic.tech/blog/revoke-jwt-before-it-expires-token-version 
</details>

A self-contained JWT can remain valid until its `exp` time because an API can validate it locally without asking the issuer whether it has been revoked. Common approaches are:

- **Short-lived access tokens:** Revoke the refresh token so no new access tokens can be issued. The current access token may still work until it expires.
- **Check revocation state:** Have the API check a token ID (`jti`), user token version, or session status in a database/cache on each request. This enables faster revocation but adds a store lookup.
- **Use token introspection:** The API asks the authorization server whether the token is active. This supports centrally managed revocation, with a network request or cached result.

OAuth defines token revocation and token introspection endpoints. Revoking a token at the issuer alone only stops its use at APIs that learn about the revocation; locally validated JWTs need a short expiry or an additional revocation check for prompt invalidation.
